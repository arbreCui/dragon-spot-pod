WHY THE ORIGINAL NORMAL CHECK DOES FIVE FULL HISTORY WALKS

For an already bootstrapped H/runtime and a normal complete window with no
invalid frame, the exact original Source calls the genuine original
DynamicHistoryResources.check at these distinct points:
  1. JointHistoryResources.check -> super().check(), before joint_bytes.
  2. persist -> monitor.record -> disk_account(first bare line length).
  3. monitor.record -> disk_account(complete enriched line length), preappend.
  4. monitor.record -> disk_account(0), postappend.
  5. joint_bytes -> monitor.base_history_check(monitor.resources), postappend,
     immediately before the unchanged final history/free/freeze/publication.

Each disk_account call performs fresh full H/O/C/D/E accounting and D/E freeze
checking, and invokes the genuine bound DynamicHistoryResources.check. That
original history method derives and validates current roots, traverses them
afresh, re-derives/validates roots after traversal, observes filesystem free
space, and applies the original history/free caps. It has no scan cache.

are three temporally separate obligations: (a) the genuine outer check before
joint_bytes, (b) a complete fresh prewrite admission for the fully enriched
actual diagnostic append, and (c) a new full postappend history/free check that
counts that actual journal before publication. There are real PS/lsof/owner
